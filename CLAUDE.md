# Reminders – custom Home Assistant integration

Private custom integration (not for HACS or core). Replaces two trigger-template sensors
(`sensor.reminders`, `sensor.dynamic_reminders`) that lost data when a Jinja render failed.
Target: Home Assistant 2026.10.4. All tests pass on HA 2026.10.4 (Python 3.14,
pytest-homeassistant-custom-component 0.13.375), checked 2026-10-31.

## Layout
- `custom_components/reminders/` – the integration (domain `reminders`)
  - `manager.py` – `ReminderManager`: data in `.storage/reminders.data` via `Store(atomic_writes=True)`;
    each change is made on a deep copy, saved, then made current, under an `asyncio.Lock`
  - `services.py` – action registration (in `async_setup`), schemas, handlers
  - `validation.py` – `trigger_time`, `whole_days`, `non_empty_text`
  - `sensor.py` – two count sensors; collection in the `reminders` attribute
  - `config_flow.py` – single confirm step; `single_config_entry` in manifest
- `tests/` – pytest-homeassistant-custom-component tests (`pytest.ini` sets asyncio auto mode)
- `README.md` – user-facing install steps and examples

Run tests (HA 2026.10 needs Python 3.14):
`uv venv -p 3.14 .venv && VIRTUAL_ENV=.venv uv pip install pytest-homeassistant-custom-component && .venv/bin/python -m pytest tests`

## Agreed design decisions (from the user)
- Sensors have no device. State = item count, always `len()` of the collection.
  `reminders` attribute holds the collection and is excluded from the recorder.
  - `sensor.reminders`: `{id: "text"}`
  - `sensor.dynamic_reminders`: `{id: {reminder, next_trigger_time, repeat_frequency, nag}}`
- Actions: `add`, `acknowledge`, `acknowledge_all`, `clear_all`, `add_dynamic`, `update_dynamic`,
  `delete_dynamic`, `clear_all_dynamic`. No initialize actions (integration creates empty data on first load).
  `acknowledge_all` and `clear_all` both empty the reminders list; both kept so caller intent is clear.
- IDs are generated by the integration (8 hex chars, `secrets.token_hex(4)`), unique across both
  collections. `add` and `add_dynamic` return `{"id": ...}` (SupportsResponse.OPTIONAL).
- Unknown ID on acknowledge / update_dynamic / delete_dynamic → fail (ServiceValidationError).
- `update_dynamic` changes only the fields passed; at least one field required.
- `next_trigger_time`: validated; date AND time required; seconds, microseconds, offset optional;
  `T` or space separator. No offset → HA local time. Stored as `isoformat(sep=" ")` with offset,
  e.g. `2026-10-31 11:33:10.095534-04:00`.
- `repeat_frequency`: whole days ≥ 0 (0 = do not repeat). `nag`: boolean. `add_dynamic` requires all four fields.
- Unknown fields are rejected. Any validation failure raises to the caller and changes nothing.
- Logging: HA's built-in per-integration "Enable debug logging". Every action call is logged at
  debug with its data *before* validation (actions registered with `schema=None` and validated in
  the handler), so rejected calls are logged too.
- Events (names as given by the user, not domain-prefixed), fired after the change is saved:
  `acknowledge` → `reminder_acknowledged` `{id, reminder}`; `acknowledge_all` →
  `all_reminders_acknowledged` `{reminders: {id: text}}` (fired even if already empty).
  `clear_all` fires nothing.
- No import from the old template sensors. Nothing else listened to the old events.
- If the storage file can't be loaded, setup fails with ConfigEntryError and the file is left untouched.
